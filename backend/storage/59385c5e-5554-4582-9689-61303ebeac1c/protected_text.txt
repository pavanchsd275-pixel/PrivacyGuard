ABSTRACT 
 
 Present scenario of the area  
In modern supply chain and retail operations, effective inventory control is vital for business 
scalability and logistical accuracy. Most enterprises currently track items, manage warehouses, 
and record transactions using computer-based inventory systems. However, a significant majority 
of traditional setups remain deployed on on-premises infrastructure. In this prevailing model, 
organizations host local database servers, web interfaces, and manual file directories within private 
physical facilities. These architectures are typically monolithic, tightly coupling inventory 
database records, file and image storage for product assets, and alert processing routines inside 
single, centralized host machines managed entirely by internal IT personnel. 
 
 Limitations and Pitfalls of the Present Scenario 
Traditional on-premises architectures impose severe operational and technical bottlenecks: 
 
Poor Scalability and High Cost: Expanding capacity requires purchasing expensive 
physical server hardware, resulting in high capital expenditure and underutilized resources 
during off-peak cycles. 
 
Single Points of Failure: Localized server or network disruptions can cause complete 
system outages, inventory discrepancies, and permanent data loss without extensive, costly 
disaster recovery setups. 
 
Data Silos and Restricted Access: Synchronizing inventory across multiple warehouse 
locations in real time is difficult, restricting cross-facility visibility and delaying stock 
audits. 
 
Synchronous Processing Bottlenecks: Tightly coupled monolithic systems struggle when 
handling resource-intensive background jobs, such as generating real-time low-stock alerts 
and processing batch updates, which degrades core transactional performance. 
 
 Problem Addressed 
This project addresses the critical need for a resilient, highly available, and scalable inventory 
management architecture that eliminates physical hardware dependency. Specifically, it tackles 
rigid relational database schemas that complicate diverse product catalog updates, the inefficiency 
of storing asset images on local disks, synchronous task bottlenecks during high-volume alert 
processing, and the security challenges of managing user credentials securely in distributed 
environments. 
 Proposed Solution 
To solve these challenges, this project introduces a Cloud-Based Inventory Management System 
built on Microsoft Azure Platform-as-a-Service (PaaS) offerings, developed as part of the Ethnus-
Microsoft Azure Fundamentals (AZ-900) internship: 
 Dynamic Data Storage: Azure Cosmos DB is employed as a multi-region, low-latency 
NoSQL document database, enabling schema-agnostic catalog management and fast 
CRUD operations for diverse stock-keeping units (SKUs). 
 Decoupled Media Management: Azure Blob Storage is integrated to store unstructured 
assets, including uploaded product photos and barcodes generated dynamically via 
Python's barcode library.

1 INTRODUCTION 
In the era of digital transformation, supply chain logistics and inventory management have evolved 
from simple ledger-based tracking to complex, data-driven ecosystems. Historically, organizations 
relied heavily on traditional on-premises systems to monitor their stock levels, manage warehouse 
operations, and facilitate order fulfillments. While these legacy systems functioned adequately for 
localized operations, they are increasingly insufficient for modern, dynamic business 
environments. On-premises infrastructures typically require substantial upfront capital 
investments, dedicated hardware maintenance, and complex disaster recovery setups. 
Furthermore, they often operate as siloed environments, leading to latency in data synchronization, 
restricted cross-location accessibility, and severe difficulties in scaling during periods of rapid 
business growth or sudden demand spikes. 
The advent of Cloud Computing has revolutionized this landscape by offering Infrastructure as a 
Service (IaaS) and Platform as a Service (PaaS) models. By migrating inventory systems to the 
cloud, organizations can leverage on-demand scalability, high availability, and globally distributed 
data centers. Microsoft Azure, a leading enterprise-grade cloud platform, provides a robust suite 
of services that allows developers to build resilient, serverless applications without the 
administrative overhead of managing physical hardware. This project, undertaken during the 
Ethnus-Microsoft Azure Fundamentals (AZ-900) internship, explores the practical transition from 
legacy inventory methods to a modernized, cloud-native architecture. By utilizing Azure's 
specialized storage and identity services alongside Python's backend capabilities, the project 
demonstrates how cloud technologies can streamline supply chain operations, enhance data 
security, and optimize performance.

2. Azure Cloud Architecture & Fundamentals 
2.1 Cloud Computing Paradigm & AZ-900 Concepts The foundation of the Cloud-Based 
Inventory Management System (CBIMS) relies on Microsoft Azure’s public cloud infrastructure. 
Concepts mastered during the Ethnus-Microsoft Azure Fundamentals (AZ-900) internship—such 
as High Availability (HA), scalability, fault tolerance, and the Shared Responsibility Model—
serve as the guiding principles for this architecture. By utilizing Platform-as-a-Service (PaaS) 
solutions, the administrative burden of maintaining physical servers is eliminated, allowing for a 
focus solely on application logic and data management. 
2.2 Azure Cosmos DB Azure Cosmos DB is utilized as the primary, globally distributed NoSQL 
database for the inventory system. The system integrates with this service using the azure-cosmos 
Python library. Cosmos DB was selected for its schema-agnostic data modeling, which easily 
accommodates varying attributes for different stock-keeping units (SKUs) without requiring 
complex migrations. It guarantees single-digit millisecond read and write latencies, ensuring real-
time inventory tracking. 
2.3 Azure Blob Storage To manage the unstructured data generated by the inventory system, 
Azure Blob Storage is implemented via the azure-storage-blob SDK. In a modern inventory 
system, items are often tracked with visual assets. Blob Storage provides a highly durable, cost-
effective repository for product images, dynamically generated barcode graphics, and exported 
CSV/PDF reports. 
2.4 Azure Queue Storage System performance and responsiveness are optimized through 
asynchronous message processing using Azure Queue Storage, integrated via the azure-storage-
queue package. Instead of forcing the application to synchronously process heavy background 
tasks—such as sending low-stock email alerts or syncing with external supplier APIs—these tasks 
are pushed as messages to a queue. Background worker processes then consume these messages 
at their own pace, ensuring the main user interface remains highly responsive. 
2.5 Security and Identity Management Security is enforced at both the cloud resource and local 
application levels. The azure-identity library is employed to handle secure, passwordless 
authentication to Azure services using DefaultAzureCredential, which suppo
anaged 
Identities and Service Principals. This ensures that connection strings and secret 
 are not 
hardcoded into the application.

3. System Implementation & Workflow 
3.1 Development Environment & Dependencies  
The application backend is developed in Python. The project isolates its dependencies within a 
virtual environment, ensuring consistency across development and production states. Alongside 
the Azure SDKs, the environment utilizes two critical third-
ibraries: barcode for 
automated barcode generation and bcrypt for secure credential 
  
3.2 Core Application Modules 
The implementation of the system is divided into four primary modules: 
 
Authentication & Access Control Module: This module handles user login and 
registration. Passwords are never stored in plain text; instead, the bcrypt library is used to 
generate cryptographic hashes w
re salting. This protects the system against 
unauthorized access and credential 
 attacks.  
 
Barcode Generation Module: Physical inventory tracking requires a bridge to the digital 
system. Upon the registration of a new product, the barcode library dynamically generates 
a unique Code128 or EAN-13 barcode graphic.  
 
Media & Storage Module: Once a barcode is generated, or a user uploads a product photo, 
this module uploads the file directly to an Azure Blob Storage container. The resulting 
public or SAS (Shared Access Signature) URI is then returned to the application.  
 
Inventory Data Module: This acts as the central data controller. It constructs a JSON 
document containing the product name, SKU, quantity, threshold limits, and the Blob URIs 
for its images. This document is then committed to Azure Cosmos DB.  
3.3 Database Design and Data Models 
Unlike relational databases, the Cosmos DB implementation utilizes a document-based structure. 
A typical item document contains: 
 
id: A unique identifier (UUID). 
 
sku: The Stock Keeping Unit string. 
 
product_name: The descriptive name of the item. 
 
quantity: Current stock level (Integer). 
 
reorder_threshold: The minimum quantity allowed before an alert is triggered. 
 
barcode_url: The Azure Blob Storage URI linking to the generated barcode image. 
3.4 Execution Workflow 
The end-to-end operational workflow of the CBIMS operates as follows: 
1. Authentication: A warehouse manager attempts to log in. The system fetches the stored 
hash from the database and verifies it using bcrypt.  
2. Item Registration: The manager inputs details for a new inventory batch. 
3. Asset Generation: The system uses the barcode library to create a visual barcode, uploads 
it via azure-storage-blob, and retrieves the URL.  
4. Data Persistence: The item data and asset URLs are written to Azure Cosmos DB.  
5. Transaction Monitoring: As items are checked out (scanned out), the quantity in Cosmos 
DB is decremented. 
6. Asynchronous Alerting: If the decrement pushes the quantity below the 
reorder_threshold, the system pushes a JSON payload to azure-storage-queue. A separate 
background function reads this queue and triggers a reorder notification to the purchasing 
department.

4. CONCLUSION 
 
The Cloud-Based Inventory Management System (CBIMS) project successfully achieves its 
objective of modernizing traditional stock tracking through a robust, cloud-native architecture. 
By leveraging Microsoft Azure’s Platform-as-a-Service (PaaS) solutions, the system 
overcomes the limitations of legacy monolithic structures, ensuring high availability, seamless 
scalability, and fault tolerance. 
Technically, the project demonstrates the powerful interoperability of Azure services. Azure 
Cosmos DB provides a schema-agnostic, low-latency foundation for managing diverse 
inventory catalogs. Azure Blob Storage cost-effectively houses unstructured assets, including 
product images and dynamically generated barcodes. Meanwhile, Azure Queue Storage 
successfully decouples resource-heavy background tasks—such as low-stock alerts—to 
maintain optimal application performance. System security is strictly enforced b
ing 
Azure Identity for secure cloud access with the bcrypt library for local credential 
  
Developed as the culmination of the Ethnus-Microsoft Azure Fundamentals (AZ-900) 
internship, this project provided invaluable hands-on experience in serverless backend 
orchestration. Future enhancements could include integrating interactive web interfaces, 
RESTful APIs for ERP synchronization, and Azure Machine Learning for predictive 
restocking. Ultimately, this project proves that adopting a cloud-first approach yields a highly 
scalable and secure solution for modern supply chain management.
